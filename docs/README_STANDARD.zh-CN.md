# README 公共规范

定稿日期：22-10-2026。试行对象：Calligra、Nickspeare、Local Context Engine。

## 目的与适用范围

README 帮助初次访问者判断项目用途、完成首次运行，并了解实际边界。英文主文档为 `README.md`，简体中文为根目录 `README.zh-CN.md`；书法项目额外提供 `README.ja.md`。语言切换链接放在开头，各语言使用同一事实依据。技术翻译需经过术语与内容复核，不能只做逐句机器转换。

只有一句定位的 Profile README 是明确例外，不适用产品 README 的完整结构。

本规范允许按项目类型裁剪，不要求用同一篇长文覆盖应用、脚本、研究和资料仓库。许可证文件及政策不由 README 重构决定。

## 默认阅读顺序

| 顺序 | 内容 | 写法与可裁剪条件 |
|---|---|---|
| 1 | 名称与一句话描述 | 一个 H1，说明实际用途；紧接语言入口、必要的演示或下载入口 |
| 2 | 阶段与真实视觉 | 有依据的 Experimental/Alpha/Beta/维护/归档状态；优先一张实际运行截图，说明看到了什么 |
| 3 | Features | 3–6 条主要能力；区分已实现、实验性路径和未实现内容，避免宣传性标签 |
| 4 | Installation / Quick Start | 可详细：平台、前提、目录、完整命令、启动地址或可执行文件、第一步操作；下载包与源码分开 |
| 5 | Testing / CI / Platform Support | 给出已有可执行命令和工作流链接，说明真实矩阵及未覆盖的平台/安装验收 |
| 6 | Known Limitations | 明确影响使用的限制、持久化/备份和权限边界，不隐藏未验证事项 |
| 7 | Roadmap | 短段落或少量条目；已实现不放入未来计划，方向不冒充承诺日期 |
| 8 | Contributing | 链接实际贡献指南、问题入口和安全报告方式；小脚本可用一段文字替代独立章节 |
| 9 | License | 准确链接当前 LICENSE，区分代码、语料、字体、图片和依赖；记录不一致，不擅自重新许可 |

截图放在介绍之后即可，不必增加空洞的“截图”标题。单用途脚本可合并 Features 与介绍、压缩 Testing/Contributing/Roadmap，但必须保留可操作用法、必要限制和许可证。资料库可将安装替换为阅读/复用方法；没有后续计划时可省略 Roadmap，不写占位内容。

## 按项目类型调整

| 类型 | 首次使用重点 | 视觉与深入材料 |
|---|---|---|
| 图形应用，如 Calligra | 已发布包、离线启动、第一幅作品、保存/导出、平台验收；UI 语言与 README 翻译分别说明 | 保留真实作品与候选界面截图；字形覆盖、来源和架构放入已有专题文档 |
| 研究/文化工具，如 Nickspeare | 浏览器与 Python 两条入口；输入证据、算法局限、复现范围和源码/发布差异 | 真实生成结果截图；语料重建、R 分析和项目地图放入开发文档 |
| 系统工具/MCP，如 LCE | OS/工具链、可执行文件、第一条查询、采集范围、MCP 路径和客户端转发边界 | 无已验证桌面截图时不以图标代替验收；用简图准确解释 Provider/Planner 关系，性能细节链接到有方法与原始数据的报告 |

## 证据要求

- 下载版本、资产文件名、是否草稿/预发布，以实际 GitHub Release 为准。源码清单版本和同名 Release 可以不同步；必须说明默认分支修改不会自动进入旧二进制。
- 安装命令来自清单、源码、现有脚本或工作流；写清工作目录、终端和先决条件。首次运行应能从空目录理解，不依赖作者本机的全局 PATH。
- 运行测试、编译、打包、渲染和真机安装验收是不同证据，不相互替代。最低工具链声明与 CI 实际测试版本分开。
- 成熟度不由项目置顶顺序、版本号或单次 CI 成功推断。整体 Alpha 与有回归覆盖的具体功能可以并存，但不要用一个 Stable 标签覆盖整个产品。
- 性能数字必须能追溯到环境、输入规模、采样方法、限制和结果；没有必要时从 README 移至专题报告。
- 权限、索引采集、保存位置、刷新丢失、导出与重放的边界影响用户操作时，应在首次使用附近解释。
- 存在许可证/生成声明矛盾时，记录具体证据并转交许可证治理；不修改法律文本、元数据或历史版本来凑齐外观。

## 视觉和徽章

优先复用经核验的真实运行截图，并写准确替代文本。只有解释实际结构时才使用架构图；GIF 必须展示真实且有说明价值的交互。不要制作虚构界面，不添加重复的装饰 SVG 或没有项目辨识度的通用图标。

徽章约 7 个是参考上限，不是配额。试行版每个 README 只保留一个指向实际 `main` 工作流的 CI 徽章；版本、许可证、平台支持可用清晰文字与证据链接表达。徽章显示成功不能替代读取当前 PR 检查结果。

## 修改与验收

每个仓库使用独立分支和 PR。文档试行只改必要 Markdown；不调整源码、测试、工作流、基线、锁文件或许可证来迁就文案。

验收顺序：

1. 核对默认分支、源文件、清单、现有 CI、实际 Release 和许可证。
2. 审阅语言版本的功能、限制、版本、命令、许可是否等价；可执行代码块应一致。
3. 运行现有 Markdown 工具，核查本地链接的存在、大小写、锚点与图片替代文本；外链分别记录成功、临时不可达和确认失效。
4. 执行适用的首次运行/示例和现有 CI。不能执行的真机或平台判断明确保留为未验证。
5. 用 GitHub Flavored Markdown 渲染后检查桌面与窄屏，确认表格/代码可局部滚动、正文无横向溢出、图片可读。预览截图不能冒充应用实测截图。
6. 请不带作者上下文的读者回答用途、安装、当前版本、测试范围、许可证与数据边界；修改具体歧义并复核翻译。
7. 仅在最终提交的必需检查通过、范围正确时合并；读取主分支回验，保留 PR、提交和证据记录。

## 本次试行结论

三个项目都能采用同一阅读顺序，而安装结构和视觉各不相同。长篇架构与性能材料无需删除，链接到专题文档即可。Nickspeare 的语料/R 内容移动到 `docs/DEVELOPMENT.md` 后，入口更短且专业流程仍可找到。LCE 的首次索引范围和设置文件示例、Nickspeare 的结果留存和重放说明，均来自独立读者发现的实际缺口。日文复核修正了“混合文字体系的竖排方向”和“历史样本/字体映射”的歧义。

后续按仓库采用这些规则，先判断内容是否必要，再决定章节长度；不要批量复制本次三个 README 的项目特有细节。
